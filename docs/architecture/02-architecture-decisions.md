# Architecture Decisions

## وضعیت تصمیم‌ها

تصمیم‌های زیر در Phase 1 و Phase 2 به‌صورت مفهومی تأیید شده‌اند. جزئیات
پیاده‌سازی، نسخه کتابخانه‌ها، سیاست‌های دقیق دیتابیس و قراردادهای نهایی
باید هنگام اجرا اعتبارسنجی شوند.

## ADR-001 --- Single Admin در نسخه اول

**وضعیت:** تأییدشده

نسخه اول یک حساب مدیر فعال دارد. سیستم باید احراز هویت و مجوزدهی واقعی
داشته باشد. طراحی داده و سرویس‌ها تا حد معقول امکان افزودن نقش‌ها در آینده
را مسدود نکند، اما RBAC چندنقشی در نسخه اول ساخته نمی‌شود.

## ADR-002 --- Independent Localization

**وضعیت:** تأییدشده

زبان‌های `en`, `fa`, `ar` مستقل از یکدیگر Draft و Publish می‌شوند. انتشار
یا ویرایش یک زبان نباید به‌طور خودکار وضعیت زبان دیگر را تغییر دهد.

## ADR-003 --- Flexible Page Builder با Block Registry

**وضعیت:** تأییدشده

Page Builder از بلوک‌های ساختاریافته و توسعه‌پذیر استفاده می‌کند. هر بلوک
دارای نوع، نسخه Schema، شناسه پایدار و props اعتبارسنجی‌شده است. Renderer
عمومی فقط به کامپوننت‌های مورد اعتماد نگاشت می‌کند. HTML/JS خام یا اجرای
پویا مجاز نیست.

## ADR-004 --- Independent Publishing

**وضعیت:** تأییدشده

انتشار برای هر Publication Unit مستقل است؛ انتشار کل سایت به‌صورت یک
تراکنش اتمیک الزامی نیست. هر واحد دارای Draft Pointer و Published
Pointer است و رویدادهای انتشار و Rollback ثبت می‌شوند.

## ADR-005 --- Dynamic CMS + GitHub Pages

**وضعیت:** تأییدشده

Frontend اولیه روی GitHub Pages میزبانی می‌شود و داده منتشرشده را در زمان
اجرا از API دریافت می‌کند. GitHub Pages Backend ندارد. محدودیت‌های SEO در
SPA و Hash Routing باید به‌صورت آگاهانه مدیریت شوند؛ امکان Pre-render یا
مهاجرت به Host دارای SSR در آینده باز می‌ماند.

## ADR-006 --- Supabase و PostgreSQL

**وضعیت:** تأییدشده به‌عنوان زیرساخت اولیه

Supabase برای PostgreSQL، Auth و Storage انتخاب اولیه است. استفاده از
قابلیت‌های اختصاصی آن باید پشت لایه Infrastructure و Repository قرار
گیرد.

## ADR-007 --- Repository Pattern

**وضعیت:** تأییدشده

UI و Application Services نباید مستقیماً Supabase Query بنویسند.
Repository Contracts در `src/application/repositories` تعریف می‌شوند و
Application Services و Use Cases از این قراردادها استفاده می‌کنند.
پیاده‌سازی این قراردادها در لایه Infrastructure قرار می‌گیرد؛ Adapter
موقت Local/Static در Phase 3 و Supabase Adapter در Phase 4 اضافه می‌شود.
Domain نباید به Repositoryهای زیرساختی، دیتابیس، Supabase یا جزئیات
Persistence وابسته باشد. این مرزبندی امکان جایگزینی Backend و مهاجرت
احتمالی به Backend خودمیزبان را حفظ می‌کند.

## ADR-008 --- Incremental Migration

**وضعیت:** تأییدشده

کد فعلی به‌صورت مرحله‌ای مهاجرت می‌کند. رفتار و ظاهر موجود باید در هر مرحله
قابل اجرا و قابل تست باقی بماند. حذف یا جایگزینی بخش‌های موجود فقط با
دلیل فنی و معیار پذیرش انجام می‌شود.

## ADR-009 --- Preserve Hash Routing Initially

**وضعیت:** تصمیم فعلی

Hash Routing فعلی بدون نیاز اثبات‌شده با Router جدید جایگزین نمی‌شود.
Routeهای Admin و Public باید به‌صورت روشن تفکیک شوند. راهبرد نهایی URL و
SEO در مرحله مناسب دوباره ارزیابی می‌شود.

## ADR-010 --- No Arbitrary Executable Content

**وضعیت:** تأییدشده

محتوای قابل مدیریت باید داده ساختاریافته باشد. هیچ مسیر اجرای JavaScript
یا HTML دلخواه از دیتابیس یا ورودی Admin ایجاد نمی‌شود.

## ADR-011 --- Figma Vite Plugins

**وضعیت:** نیازمند تصمیم اجرایی

`vite.config.ts` شامل Pluginهای اختصاصی Figma است. تا زمانی که وابستگی
پروژه به Figma Make بررسی نشده، حذف یا بازنویسی آن‌ها مجاز نیست. در Phase
3 باید مسئولیت هر Plugin، ضرورت آن و اثرش بر Build/Preview مشخص شود.

## قواعد ثبت ADR جدید

هر تصمیم مهم جدید باید شامل این بخش‌ها باشد: - شناسه و عنوان - وضعیت:
Proposed / Accepted / Rejected / Superseded - تاریخ - زمینه و مسئله -
تصمیم - گزینه‌های جایگزین - پیامدهای مثبت و منفی - مراحل مهاجرت - تست‌ها و
مستندات مرتبط
